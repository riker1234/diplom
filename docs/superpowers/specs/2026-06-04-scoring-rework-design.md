# Переработка распределения баллов в движке рекомендаций (СППР)

Дата: 2026-06-04
Статус: дизайн согласован, ожидает вычитки

## 1. Контекст и цель

Движок рекомендаций (`backend/app/recommendation/engine.py`) ранжирует товары
«сырой» суммой целых баллов из трёх блоков: репутация бренда, использование
бюджета, качество характеристик. Итог нельзя интерпретировать («почему 14?») и
он несравним между категориями (у монитора потолок ТТХ +6, у коврика +2).

Недавно добавлены поля рейтинга/отзывов по источникам
(`ozon/citilink/wb` × `rating/reviews`), но **в скоринге они не участвуют**.

**Цель (комплексная переработка):**
1. Привести итог к единой понятной шкале **0–100**, сравнимой между категориями.
2. Задействовать **рейтинг/отзывы** как сигнал качества — сильнее бренда.
3. Углубить оценку **характеристик**, особенно для бедных сейчас категорий
   (наушники, микрофон, коврик).

**Принцип:** «хороший девайс = качество характеристик + реальная
удовлетворённость покупателей»; бренд — лишь слабый репутационный априор, потому
что популярный бренд может выпускать ненадёжные модели (кейс Razer: имя топовое,
а часть линейки быстро ломается — это видно в отзывах, но не в бренд-пирамиде).

## 2. Текущее состояние (что меняем)

- `recommend()` — точка входа: фильтр-выборка → `_score()` по каждому товару →
  сортировка по убыванию балла, вторичная по цене в зависимости от приоритета.
- `_score()` возвращает `(score:int, breakdown:list)`; `breakdown` показывается в
  карточке — **этот контракт сохраняем** (прозрачность — фича).
- `_build_query()` — жёсткие фильтры (бюджет, тип подключения, форм-фактор и т.д.) —
  **остаётся без изменений**, меняем только скоринг отобранных товаров.
- `_BRAND_TIER` (ручная пирамида брендов) — **удаляется**; бренд вычисляется из
  реальных оценок (см. §3.4), чтобы тиры были фактом, а не мнением.

## 3. Новая модель: взвешенная сумма 4 под-оценок (0–100)

`итог = round( ТТХ·wA + Рейтинг·wB + Бренд·wC + Цена·wD )`,
где каждая под-оценка ∈ [0,100], а веса (w) зависят от приоритета и в сумме = 1.

### 3.1. Веса по приоритету

| Компонент | Бюджет | Баланс | Флагман |
|-----------|:------:|:------:|:-------:|
| A. Характеристики (ТТХ) | 0.30 | 0.40 | 0.45 |
| B. Рейтинг/отзывы | 0.30 | 0.30 | 0.20 |
| C. Бренд (пирамида) | 0.05 | 0.12 | 0.20 |
| D. Соответствие бюджету | 0.35 | 0.18 | 0.15 |

Сумма каждого столбца = 1.00. Рейтинг ≥ бренда во всех режимах.

### 3.2. Компонент A — Характеристики → 0–100

Базируется на текущих правилах `_score()` (вес/DPI у мыши, Гц/матрица у монитора
и т.д.), но **нормируется по известным критериям**:

`A = (сумма набранных бонусов) / (макс по тем критериям, для которых есть данные) · 100`

- Нормируем по **известным** критериям, не по полному максимуму — товар не
  топится за отсутствие поля (`max_dpi=NULL` не штрафует).
- Если по товару нет ни одного релевантного ТТХ-поля → `A = 50` (нейтрал).
- Штрафы (отрицательные правила, напр. «игровой монитор для работы») остаются и
  могут опускать `A` ниже нейтрала, но не ниже 0.

Углубление бедных категорий (предложение, уточняется при вычитке):

| Категория | Сейчас учитывается | Добавить |
|-----------|--------------------|----------|
| mouse | вес, max_dpi (gaming) | button_count (office: >2 — удобно), вес для office |
| keyboard | switches-match, form_factor, key_count | keycap_material (PBT > ABS), keycap_manufacturing |
| monitor | refresh_rate, matrix, resolution | response_time_ms (gaming: ≤1мс +) |
| headphones | has_microphone | impedance_ohm (низкий — легче раскачать), frequency_response, конструкция под use_case |
| microphone | mic_type, usb | directionality (кардиоида для стрима), xlr для recording |
| mousepad | rgb-match | surface_material (контроль/скорость), thickness_mm |

### 3.3. Компонент B — Рейтинг → 0–100

1. **Выбор источника:** берём оценку источника с **наибольшим числом отзывов**
   (как уже делает карточка). `R` — оценка, `v` — число отзывов этого источника.
2. **Сглаживание по количеству** (Байес), чтобы «5.0 из 3 отзывов» не вылезало:
   `adj = R·v/(v+m) + C·m/(v+m)`, где `m = 50` (порог доверия), `C = 4.3`
   (типичное среднее маркетплейса = нейтральный приор).
3. **Растяжка верхней зоны** (оценки живут в 4.4–4.9):
   `B = clamp((adj − 4.0) / 1.0 · 100, 0, 100)`.
   → 4.4→40, 4.6→60, 4.8→80, 4.9→90, 5.0→100; ≤4.0→0.
4. **Нет рейтинга ни в одном источнике** → `B = 50` (нейтрал; на ранжирование не
   влияет, работает бренд-априор через свой компонент).

Параметры `m=50`, `C=4.3`, нижний порог `4.0` — настраиваемые константы.

### 3.4. Компонент C — Бренд (из данных) → 0–100

Тир бренда **вычисляется из БД**, а не задаётся вручную (ручной `_BRAND_TIER`
удаляется). Это снимает субъективность: «почему Logitech выше Acer» отвечается
цифрой, а не мнением.

- `brand_avg` = средний рейтинг товаров этого бренда **в той же категории**,
  взвешенный по числу отзывов:
  `Σ(rating_i · reviews_i) / Σ(reviews_i)` по товарам бренда, у которых есть
  оценка (`rating_i` — представительная оценка товара, как в §3.3).
- Нормализация **той же растяжкой**, что и рейтинг:
  `C = clamp((brand_avg − 4.0) · 100, 0, 100)`.
- **Надёжность:** если у бренда в категории суммарно мало отзывов
  (`Σreviews < 30`) или нет оценённых товаров → `C = 50` (нейтрал). Опционально:
  перед откатом расширить усреднение на все категории бренда.
- **Самовключение:** товар входит в среднее своего бренда; для бренда с 1 товаром
  это эхо компонента B, но такие бренды обычно не проходят порог надёжности →
  нейтрал. Для мультибренда влияние пренебрежимо.
- **Цена в тир не входит** (двойной учёт — цена это компонент D).
- **Защищаемость ВКР:** тиры брендов — вычисленный факт из реальных оценок
  покупателей по собственной базе, воспроизводимо.

### 3.5. Компонент D — Соответствие бюджету → 0–100

От `ratio = best_price / budget` (best_price — мин. цена по источникам):
- **Бюджет:** чем дешевле в разумных рамках, тем выше. Пик при ratio≈0.15–0.50→100,
  далее плавно вниз; слишком близко к потолку — ниже.
- **Баланс:** пик при ratio≈0.50–0.75→100, по краям тейпер; <0.15 — занижаем
  («подозрительно дёшево»).
- **Флагман:** чем ближе к потолку, тем выше: ratio≥0.75→100, <0.40→низко.
- Бюджет не задан → `D = 50`.

## 4. Сортировка и вывод

- Сортировка: по убыванию итогового 0–100. Шкала непрерывная — точные ничьи
  редки; вторичный ключ оставляем как сейчас (флагман — дороже, бюджет — дешевле,
  баланс — ближе к середине бюджета).
- `_score()` возвращает `(score, breakdown)`, где `score` ∈ [0,100], а `breakdown`
  — список вкладов **по 4 компонентам** в баллах итоговой шкалы
  (напр. «Рейтинг 4.8 · 900 отз. → +23», «Бренд Razer: ср. 4.5 → +12»,
  «ТТХ: 58 г, 30000 DPI → +40», «Цена 70% бюджета → +17»).
  Контракт `score_breakdown` для фронта сохраняется;
  фронт менять не обязательно.
- Топ-20 — без изменений.

## 5. Обработка пропусков данных (сводно)

| Нет данных | Поведение |
|------------|-----------|
| ТТХ-поле | не входит в нормировку (не штраф) |
| все ТТХ-поля | A = 50 |
| рейтинг | B = 50 |
| бренд ненадёжен (Σотзывов < 30) | C = 50 |
| бюджет не задан | D = 50 |

## 6. Контрольный пример (проверка эффекта Razer)

Мышь, «для игр», «Баланс», бюджет 6000 ₽:

| | X: Razer (тир3), 5500₽, 58г/30000, 4.4(1600) | Y: средний (тир1), 4200₽, 55г/26000, 4.8(900) |
|--|--|--|
| A ТТХ | 100 | 100 |
| B Рейтинг | 40 | 77 |
| C Бренд (ср. рейтинг бренда) | 50 (ср. ≈4.5) | 60 (ср. ≈4.6) |
| D Цена | 60 | 95 |
| **Итог** | **≈69** | **≈87** ✅ |

Расчёт (веса «Баланс» 0.40/0.30/0.12/0.18):
- X = 100·0.40 + 40·0.30 + 50·0.12 + 60·0.18 = 40 + 12 + 6 + 11 = **69**
- Y = 100·0.40 + 77·0.30 + 60·0.12 + 95·0.18 = 40 + 23 + 7 + 17 = **87**

Y (средний бренд, честный 4.8) уверенно обходит X (Razer, 4.4) — целевой эффект;
с брендом-из-данных разрыв даже больше, т.к. имя Razer больше не даёт бонуса «по
репутации».

## 7. Вне рамок (non-goals)

- Жёсткие фильтры `_build_query()` — не трогаем.
- Анкета/вопросы (`questions.py`) — не меняем (тех же ответов достаточно).
- `setup_engine.py` (сборка комплекта) — отдельный движок; согласование с новой
  моделью — отдельной задачей, не в этой переработке.
- Фронт — менять не обязательно (контракт `score`/`score_breakdown` сохранён);
  при желании позже показать «X/100».

## 8. Проверка

- Юнит-тесты на под-оценки B (сглаживание/растяжка), C (нормализация тиров),
  D (кривые по приоритету) и на A-нормировку с пропусками.
- Контрольный пример из §6 как регрессионный тест (Y > X).
- Прогон `recommend()` по нескольким реальным выборкам из прод-БД, ручная
  проверка вменяемости топ-5.
